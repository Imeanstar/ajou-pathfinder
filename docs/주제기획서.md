## 1. 주제

### 1-1. 한 문장 정의

> **아주대 3학년이 성적표를 올리고 원하는 진로를 고르면, 요람 기준 졸업 현황을 정리하고 남은 학기에 들을 과목과 참여할 교내 프로그램을 학기별 로드맵으로 제안하는 서비스.**

### 1-2. 주제 선정 경과 (기각된 안과 그 이유)

| 검토안 | 기각 사유 |
|---|---|
| AI 컴플라이언스 코파일럿 | 데모 임팩트 부족, 사용자 페르소나 협소 |
| 1차 "내돈예산" 고도화 | 1차와 동일 재료 → 차별성 부재, 3연속 동일 주제 |
| 공공데이터 AI 친화성 진단기 | RAG 지식원 단일 → Advanced RAG 요구 미충족 |
| 계약서 독소조항 검출기 | 팀 관심도 미달 |
| 전세사기 위험 진단 | 외부 API 2종 의존 → 2일 완주 리스크 |
| 청년정책 매칭 | 본질이 조건 필터링 → RAG 필연성 약함 |
| 음식점 위생 알림 (식약처) | **정형 테이블 데이터 → RAG 필연성 없음**, Multi-Agent 필연성 없음, PII/가드레일 부재, "알림"이 시연 불가(시간 경과 필요), 1차와 동일 형태(공공데이터+지도+챗봇) |
| **졸업사정 단독** | **졸업 가능 여부는 학교 포털이 이미 제공** → 문제 정의가 약함 |

**최종 선정: 졸업사정 + 진로 컨설팅.** 졸업사정 단독의 약한 문제 정의를 "진로 기반 로드맵 컨설팅"으로 전환하여 해결.

### 1-3. 왜 이 주제인가

**문제 정의가 실재한다.** "졸업 가능한가"는 답해주는 주체가 이미 있다. 그러나 **"백엔드 개발자가 되고 싶은데, 남은 학기에 뭘 듣고 뭘 참여해야 하나"** 는 아무도 답해주지 않는다.

- 학사팀 → 학점만 본다
- 취업지원팀 → 프로그램만 안다
- 창업지원단 → 창업만 안다
- 아주허브 → 프로그램이 수백 개인데 나에게 맞는 게 뭔지 알려주지 않는다

**정보가 부서별로 파편화되어 있고, 이를 통합해 개인화하는 주체가 없다.** 이것이 핵심 문제 진술.

**대상 학번: 2025학번으로 확정 (2026-08-20 팀 결정).** 애초 "3학년"으로 잡았던 논리 — 1학년은 시간이 남아 무의미하고 4학년은 이미 늦었으니, 남은 결정이 결과를 바꾸는 구간이 필요하다는 것 — 는 유지하되, "3학년"을 "2025학번"으로 구체화했다. 2025학번은 2026-2학기 기준 **2학년 2학기에 진입**하며 **128학점 신 교육과정을 적용받는 첫 학번**이다. 이 학번을 고른 이유는 두 가지다.

1. 남은 학기가 5개 이상으로, 3학년보다 더 결정의 영향력이 크다.
2. **신 교육과정 첫 적용 학번이라 참고할 선배 사례가 없다.** 위에서 말한 "정보 파편화" 문제가 이 학번에서 구조적으로 가장 심하다 — 선배에게 물어봐도 자신들이 겪은 구 교육과정(140학점) 기준이라 그대로 안 통한다.

### 1-4. 차별점 3가지

1. **파편화된 교내 정보를 하나로 묶는다** — 요람(졸업요건) + 아주허브(비교과) + 교육과정표(과목)를 교차 검색
2. **ChatGPT가 못 하는 일을 한다** — ChatGPT는 아주대 요람도, 이번 학기 개설 강의도, 다음 주 마감인 아주허브 프로그램도 모른다. 이것이 RAG를 쓰는 이유이며, 발표에서 ChatGPT 답변과 나란히 비교 제시
3. **모든 추천에 근거를 인용한다** — 요람 조항 / 프로그램 원문 링크. 근거가 없으면 판정 자체를 거부

### 1-5. 서비스 이름

**AJOU Pathfinder** (가제, 2026-08-20 확정). GitHub 저장소명(`ajou-pathfinder`)과 일치.

`③진로 목표·자기신고 입력` 순으로 진행한다. ③ **어학 성적과 프로그래밍 역량 인증을 화면에서 직접 고를 수 있게** 했다

**전공필수가 "N/10개"인 이유**: 학점 합산이 아니라 요람이 정한 10개 특정 과목(자료구조·알고리즘·운영체제 등)을 전부 들었는지 보는 **집합 완전성 판정**이다. 미이수 과목명이 그대로 부족 항목으로 표시된다.

**일반과정을 택하면 표시가 달라진다**: 전공선택 기준이 10학점으로 낮아지고, 산학프로젝트 인증은 1개로 낮아지지만, 대신 `⚠️ 복수전공/부전공 — 이 서비스 범위 밖입니다. 학사팀에 문의하세요`가 추가된다(심화과정에만 없는 요건이라 우리 데이터로 판정 불가 — 5-1 범위 결정 참고).

**산학프로젝트 인증의 판정 방식이 다른 항목과 다르다.** 학점 합산이 아니라 **이수 과목이 6개 과목군(집중교육/자기주도프로젝트/현장실습/창업실습/캡스톤디자인/자기주도연구) 중 하나에 속하는지**를 세는 집합 판정이다. 이수 과목 코드 목록을 과목군 집합과 대조하는 것도 **순수 코드**(LLM 미사용)로 처리한다 — 3-1 설계 원칙 ①의 또 다른 사례.

`[근거 보기]` → **요람 원문 조항이 그대로 펼쳐진다.** 판정만 던지지 않고 출처를 함께 제시하는 것이 신뢰 장치.

역량 레이더 — 목표 트랙 요구 역량(점선)과 현재 이수 내역 기반 역량(실선)을 겹쳐 표시. **벌어진 축이 곧 해야 할 일.**

```
자료구조·알고리즘  ████████░░  80%
데이터베이스       ██████░░░░  60%
클라우드·인프라    ██░░░░░░░░  20%   ← 최대 격차
협업·PM           ███░░░░░░░  30%
```

출처별로 색을 나눠 표시한다.

```
클라우드·인프라   ████████░░  75%
                  ██████      검증(과목 이수)
                        ██    자기신고
```

## 3. 에이전트 아키텍처

```
                    ┌─────────────────┐
  성적표 PDF ──▶    │   Supervisor    │  ◀── 진로 트랙 선택
  (PII 마스킹)      │   (라우팅·통합)  │  ◀── 개인 프로젝트 (수기)
                    └────────┬────────┘
         ┌───────────┬───────┴───────┬────────────┐
         ▼           ▼               ▼            ▼
   ┌──────────┐ ┌─────────┐  ┌────────────┐ ┌──────────┐
   │ 졸업요건  │ │ 역량진단 │  │  교과추천   │ │ 비교과추천│
   │  판정     │ │         │  │            │ │          │
   │ 계산=코드 │ │트랙가중치│  │교육과정 RAG│ │아주허브RAG│
   │ 근거=RAG  │ │×이수내역 │  │            │ │          │
   └──────────┘ └─────────┘  └────────────┘ └──────────┘
         └───────────┴───────┬───────┴────────────┘
                             ▼
                    ┌─────────────────┐
                    │  로드맵 배치     │  선수과목·개설학기·마감일 제약
                    │  (Sequential)   │  → 학기별 타임라인
                    └─────────────────┘
```

### 3-1. 설계 원칙 ① 계산은 코드, 판단은 LLM

- **결정론적 파이썬**: 학점 합산, 이수구분 집계, 요건 충족 여부 산술
- **LLM**: "이 과목이 요건을 대체할 수 있는가", "이 프로그램이 이 역량에 맞는가"

제출양식 SECTION 07의 `일반 로직과 경계 — LLM이 하지 않는 것` 칸을 이것으로 채운다.

### 3-2. 설계 원칙 ② 추천은 생성이 아니라 선택 (closed-set)

프로그램·과목은 **수집한 DB 안에서만** 고르게 하고, LLM은 고른 이유를 설명만 한다.
**없는 프로그램을 지어낼 경로 자체를 제거** — 환각 대응의 근본 해법.

### 3-3. 설계 원칙 ③ 자기신고는 가중치를 낮춘다

| 입력원 | 검증 여부 | 가중치 |
|---|---|---|
| 이수 과목 (성적표) | 검증됨 | 1.0 |
| 비교과 이력 (자기신고) | 미검증 | 0.5 |
| 개인 프로젝트 (수기 입력) | 미검증 | 0.5 |

화면에서도 출처를 색으로 분리 표시한다.

> 발표 예상 질문 *"자기신고를 어떻게 믿죠?"* → **"믿지 않습니다. 가중치를 절반으로 두고 출처를 분리해 표시합니다."**

## 4. 역량 온톨로지와 진로 트랙

### 4-1. 구조

트랙마다 역량 맵을 손으로 쓰면 비용이 폭증한다. 대신:

- **역량 온톨로지 12~15개**를 한 번만 정의
- **트랙은 그 역량들의 가중치 벡터**로 정의 → 트랙 추가 비용 = "숫자 15개 채우기"
- **과목·프로그램·프로젝트 분야에 역량 태그**를 달아둔다

**역량 16개 (2026-08-20 개정 — 13개에서 도메인 지식 3개 추가):**
기술 역량 13개(기존): 자료구조·알고리즘 / 시스템·네트워크 / 데이터베이스 / 클라우드·인프라 / 웹·프론트엔드 / 데이터·ML / 보안 / 소프트웨어공학·설계 / 협업·PM / 커뮤니케이션·문서화 / 연구·분석 / 창업·비즈니스 / 문제해결·코딩테스트
도메인 지식 3개(신규): 금융·핀테크 지식 / 모빌리티·임베디드 지식 / 공공정책·행정 이해

**산학프로젝트 인증 6개 과목군과 자연스럽게 연결됨**: 창업실습→창업·비즈니스, 자기주도연구→연구·분석, SW캡스톤디자인→협업·PM. 같은 과목을 들으면 졸업요건도 채우고 역량도 채운다는 설명이 로드맵 화면에서 그대로 나온다(3-1 참고).

**축 추가 vs 축 분할의 비용 차이**: 도메인 지식 3개는 기존 63개 과목 태깅을 재작업하지 않고 추가했다(기존 과목들은 이 3개 축에 대해 0으로 남는 게 정확한 값 — SW 전공 과목이 실제로 금융·자동차·공공 도메인 지식을 안 주기 때문). 반면 "시스템·네트워크"를 "시스템"과 "통신"으로 쪼개는 건 기존 태깅 전체를 다시 봐야 해서 비쌌다(4-2 참고) — **새 축 추가는 싸고, 기존 축 분할은 비싸다**는 게 이번에 확인된 설계 원칙.

### 4-2. 진로 트랙 — 역할 8개 × 산업 오버레이 3개 + 대학원 연구실 클러스터 (2026-08-20 개정)

기존 7개(백엔드/프론트엔드/풀스택/AI·데이터/보안/기획·PM/대학원·연구)를 요람 1페이지 "졸업 후 진로" 원문에 맞춰 갈아엎었다:

> "정보통신·시스템·보안 등 SW 관련 기업 및 **금융, 자동차, 공공기관** 등 응용 산업체 진출 / **프로그래머, SW디자이너, SW아키텍트, 시스템 엔지니어, 통신 전문가** 등 다양한 직종 진출 / 대학원 진학 / **창업**"

요람 문구가 실은 **두 축**이라는 걸 확인했다 — 직무 유형(프로그래머/SW디자이너/SW아키텍트/시스템 엔지니어/통신 전문가)과 산업 도메인(금융/자동차/공공기관). 산업 도메인은 SW과 과목만으로는 구분이 안 되지만(모든 산업이 똑같은 기술 역량을 요구), 아주허브 실측(2026-08-20)으로 도메인 특화 프로그램이 실제로 존재함을 확인해 **오버레이(2차 선택)로 별도 설계**했다.

**1차 선택 — 역할 트랙 8개 (필수)**

| 트랙 | 요람 근거 | 비고 |
|---|---|---|
| 백엔드 프로그래머 | "프로그래머" | 기존과 동일 |
| 프론트엔드 프로그래머 | "프로그래머" + "SW디자이너" | SW디자이너를 흡수 — 단, UI/UX 전공과목이 없어 완전한 디자인 역량 대변은 못 함(한계, 아래 참고) |
| **SW아키텍트** | "SW아키텍트" | **풀스택 대체.** 특정 레이어를 얕게 훑기보다 전체 설계·인프라를 아우르는 역할로 재설계 |
| AI·데이터 엔지니어 | (명시 없음) | 유지 — 요람 문구엔 없지만 실제 커리큘럼이 AI 과목(AI집중교육1·2, 인공지능입문 등 전공필수 포함)을 깊게 다뤄 유지가 타당하다고 판단 |
| **시스템·네트워크 엔지니어** | "시스템 엔지니어" + "통신 전문가" | **신규.** 기존엔 이 역량축이 백엔드 트랙에 묻혀 전담 트랙이 없었음 |

| 기획·PM | "창업" | 유지 — 창업·비즈니스 역량으로 이미 흡수돼 있음 |
| 대학원·연구 | "대학원 진학" | 유지, 아래 연구실 클러스터로 세분화 |

**알려진 한계 두 가지**: ① SW디자이너를 프론트엔드에 완전히 흡수하는 건 부정확하다 — 우리 커리큘럼엔 UI/UX 디자인 과목이 없다(웹시스템설계·인간과컴퓨터상호작용이 가장 근접). "프론트엔드 프로그래머"로 정직하게 이름 붙였다. ② 시스템 엔지니어와 통신 전문가는 지금 온톨로지로는 구분이 안 된다 — 둘 다 "시스템·네트워크" 하나의 축에 걸리기 때문에, 진짜로 나누려면 이 축을 쪼개야 하는데 기존 63개 과목 태깅을 다시 해야 해서 비용 대비 효과가 낮다고 판단해 합쳤다.

**필드 3개.** 제목 / 분야(드롭다운) / 형태(개인·팀).

- **분야는 드롭다운이 정답.** 역량 온톨로지에 미리 연결해두면 매핑이 무료이고 환각이 원천 불가능. `기타`만 자유 입력을 열어 그때만 LLM 호출 → LLM 호출 절감(FinOps 항목에 기술)

- **저장은 브라우저 `localStorage` + 세션 State.** 서버에 올리지 않아 PII 정책과 충돌하지 않는다

**이 기능이 메우는 구멍**: 성적표만으로는 학점 A·프로젝트 0인 학생과 학점 B·프로젝트 3개인 학생을 구분할 수 없다.

## 6. 가드레일 / Responsible AI

| 위험 | 대응 |
|---|---|
| **PII 노출** | 원본 PDF 이미지는 Gemini에 **전송하지 않음**(이미지 픽셀엔 텍스트 마스킹이 안 통함). `pdfplumber`로 텍스트+좌표 추출 → 라벨(성명/학번 등) 기반 위치 탐지·제거 → 잔여 PII 패턴 스캐너로 2차 검증(걸리면 업로드 거부, fail-closed) → **마스킹된 텍스트만** LLM 전송. 학번은 해석 없이 통째로 제거(입학년도는 사용자가 화면에서 직접 입력하므로 학번 파싱 불필요). 서버 디스크·DB 저장 없음. 상세 메커니즘은 실행계획 Task 3-1 |
| **프롬프트 인젝션 (문서 경로)** | 성적표 PDF에 지시문 삽입 → 탐지 후 차단. **악성 샘플 준비하여 시연** |
| **프롬프트 인젝션 (입력 경로)** | 프로젝트 제목 자유 텍스트에 지시문 삽입 → 탐지 후 차단. 방어 on/off 비교 시연 |
| **환각 — 없는 프로그램 생성** | closed-set 선택 구조로 경로 자체 제거 |
| **환각 — 근거 없는 판정** | 요람 조항 인용을 강제. 근거를 못 찾으면 **판정을 거부**하고 학사팀 문의를 안내 |
| **자기신고 신뢰도** | 가중치 0.5, 출처 분리 표시, `[자기신고]` 태그 |
| **책임 범위** | "졸업 여부를 확정하지 않는다. 학사팀에 무엇을 물어야 하는지 특정해준다"는 포지셔닝을 UI와 발표에 명시 |

**인젝션 방어 시연 경로가 2개** (문서 + 입력) 확보된 것이 이 주제의 강점.

## 7. 평가 설계 (2층 구조)

제출양식 SECTION 12가 정량·정성 양쪽을 요구하므로 이 구조가 양식에 정확히 대응한다.

## 8. 코드 구조

```
data_pipeline/
  01_fetch_programs.py    아주허브 npiKeyId 순회 → programs.json (300~500건)
  02_parse_yoram.py       요람 PDF → 졸업요건 + 교육과정표 구조화
  03_tag_competency.py    과목·프로그램에 역량 태그 부여 (LLM 배치, 1회성)
  competency.yaml         역량 12~15개 + 트랙 6개 가중치 벡터   ← 손으로 작성

app/
  parser.py       성적표 PDF → 이수 과목 리스트 (Gemini 멀티모달)
  masking.py      PII 마스킹 (이름·학번·주민번호)              ← Guardrail
  audit.py        졸업요건 계산 — 순수 파이썬, LLM 없음         ← 결정론
  retrieval.py    hybrid 검색 + rerank                        ← 1차 코드 재사용
  agents/         supervisor / 역량진단 / 교과추천 / 비교과추천 / 로드맵배치
  guardrail.py    인젝션 탐지 · 근거 없는 답변 차단 · 면책
  api.py          FastAPI
  static/         업로드 화면 + 통합 대시보드(현황·로드맵·챗봇) 2개

eval/
  golden_set.json  졸업판정 정답 20건 → 정밀도·재현율
  judge.py         추천 품질 LLM-as-a-Judge 루브릭

mcp_server/
  server.py        졸업요건 판정을 MCP 도구로 노출 (FastMCP + @mcp.tool)
```

### 8-1. 1차 프로젝트에서 재사용하는 것

- `retrieval.py` — 하이브리드 검색(TF-IDF + 임베딩) · 재정렬
- FastAPI 서빙 구조 (`/health`, 정적 파일 서빙)
- **대체 경로(fallback) 패턴** — API 키·쿼터·장애 시에도 서비스가 죽지 않는 구조

이것이 하루를 벌어준다.

### 8-2. MCP 활용에 대한 정직한 평가

학사 시스템 연동은 불가능하므로 MCP가 자연스럽게 붙는 주제는 아니다.
→ **"졸업요건 판정 엔진"을 자체 MCP 서버로 노출**하는 방식으로 충족시킨다.
"다른 에이전트가 우리 판정 엔진을 표준 도구로 쓸 수 있게 했다"는 설계로 설명 가능.

## 9. 범위 (Scope)

### Must

- 성적표 파싱 + PII 마스킹
- 과정 구분(심화/일반/복수) 입력
- 졸업요건 현황 — **총 이수학점(128, 평점 2.0) + 산학프로젝트 인증(과목군 집합 판정) 포함**, 요람 근거 인용
- 진로 트랙 선택
- 개인 프로젝트 수기 입력 → 역량 반영
- **학기별 로드맵 생성** (과목 + 프로그램)
- 각 추천에 근거 표시

### Should

- 대화로 어학·**TOPCIT/APC/전국대회(심화과정)**·봉사 등 미기재 요건 보완 (세션 State)
- 로드맵 수정 요청 반영
- 인젝션 방어 on/off 시연 모드

### Could

- 강의 시간표 충돌 검사
- 포트폴리오 초안 생성

### 제외 (SECTION 04.2에 사유와 함께 기록)

- **소프트웨어학과 외 학과** — 요람 형식이 학과마다 상이. 업로드형 범용 구조로 확장 가능
- **일반/복수과정의 복수전공·부전공 요건 판정** — 타 학과 커리큘럼 데이터 없어 판정 불가. "서비스 범위 밖 — 학사팀 문의"로 명시 안내만 (2026-08-20 결정, 5-1 참고)
- **실제 수강신청 연동** — 불가능
- **졸업 여부 최종 확정** — 우리는 학사팀에 무엇을 물어야 하는지를 특정해줄 뿐
